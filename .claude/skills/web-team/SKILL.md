# 하네스 웹팀 실행 (오케스트레이터)

당신은 이 팀의 **오케스트레이터**입니다. 직접 역할극("~관점에서 보면...")을 하지 말고, 아래 단계마다 **Agent(서브에이전트) 도구로 `.claude/agents/`의 해당 에이전트를 실제로 호출**해 결과를 받으세요.

**실행 모드: 서브 에이전트.** 분석 역할들은 독립 산출물만 반환하면 되고 상호 토론이 필요 없으므로, 팀 통신 대신 병렬 서브에이전트 호출을 사용합니다. 서브에이전트는 대화 기록을 볼 수 없으므로, 위임할 때마다 ① 사용자 요청 원문 ② 브리프 파일 경로 ③ 이전 단계의 핵심 결정을 프롬프트에 포함해야 합니다.

## 0단계 — 컨텍스트 확인과 브리프 (오케스트레이터 직접)

**0-1. 실행 유형 판별**

- `site/` 가 placeholder 상태(빈 캔버스)이고 요청이 신규 제작 → **초기 실행**: 0-2로.
- `site/` 에 기존 페이지가 있고 요청이 그 페이지의 수정·보완 → **후속 실행**: 기존 브리프(`references/briefs/`)를 찾아 로드하고 0-3으로. 브리프에 없는 새 요구가 있으면 브리프를 갱신하고 갱신 내용을 사용자에게 보고합니다.
- 문구 한두 개 수정처럼 작은 요청 → **부분 실행**: 관련 에이전트만 씁니다(예: copywriter → frontend-builder → qa-reviewer). 단, **qa-reviewer 검수는 규모와 무관하게 생략하지 않습니다.**
- 요청이 기존 페이지와 무관한 새 페이지 → 초기 실행으로 취급하되, 기존 `site/` 를 덮어쓴다는 사실을 사용자에게 알립니다.

**0-2. 브리프 생성 (초기 실행)**

사용자 요청으로부터 `references/briefs/<프로젝트-슬러그>.md`를 작성합니다. 브리프는 팀 전체의 범위 근거이므로 이 단계를 건너뛰지 않습니다. 형식은 `references/briefs/travel-booking.md`(예시)를 따릅니다:

- 제품 상황 (목적, 주 사용자)
- 핵심 사용자 흐름 (페이지에서 끊기면 안 되는 순서)
- 사용자 불안 / 결정 장벽
- 이번 MVP에 포함할 것 / 제외할 것 (결제·로그인·외부 API·실서버는 항상 제외)
- 디자인 방향 (선택 — 기본은 `references/design-tokens.md`)
- 데이터 방향 (선택 — 핵심 엔티티)

요청만으로 채울 수 없는 항목은 합리적 기본값으로 채우되, 사용자 확인이 필요한 결정은 최종 보고의 "남은 확인 질문"에 남깁니다. 요청이 비어 있으면 사용자에게 무엇을 만들지 물어봅니다.

**0-3. 규모 판단** — 페이지 신규 제작·구조 변경이면 전체 단계, 작은 수정이면 부분 실행.

## 1단계 — 분석·설계 (병렬 위임)

아래 에이전트들은 모두 읽기 전용이므로 **하나의 메시지에서 병렬로 호출**합니다. 각 위임 프롬프트에 사용자 요청 원문과 브리프 경로를 포함합니다.

| 에이전트 | 받아올 것 |
| --- | --- |
| `business-researcher` | 사용자 불안·비교 기준·신뢰 신호 분석 |
| `product-planner` | Must/Should/Won't 범위와 완료 기준 |
| `ux-designer` | 핵심 흐름과 상태(0건, 불가/품절) 설계 |
| `design-system-specialist` | 토큰 기준 디자인 점검·적용안 |
| `copywriter` | 화면 문구 제안/교정표 |
| `data-backend-architect` | DB 이전 가능한 mock 스키마 |

## 2단계 — 작업 지시서 종합 (오케스트레이터 직접)

여섯 결과를 하나의 작업 지시서로 합칩니다.

- product-planner의 **Won't 목록이 최우선 규칙**입니다. 다른 역할의 제안이라도 Won't에 해당하면 제외하고, 제외 사실을 기록합니다.
- 역할 간 충돌(예: 디자인 제안 vs 카피 제안)은 오케스트레이터가 판단해 결정하고 사유를 남깁니다.
- 지시서 구성: ① 구현 항목(완료 기준 포함) ② 문구표 ③ 데이터 스키마 ④ 디자인 토큰·교정값 ⑤ 하지 말 것

## 3단계 — 구현 (frontend-builder 위임)

`frontend-builder`에게 2단계 작업 지시서 전체와 브리프 경로를 프롬프트로 전달합니다. 파일 수정은 이 에이전트만 합니다. 오케스트레이터가 직접 `site/` 파일을 고치지 않습니다.

## 4단계 — 검수 (qa-reviewer 위임)

`qa-reviewer`에게 **이번 작업의 요구사항 목록**(2단계 지시서의 구현 항목)과 브리프 경로를 프롬프트에 포함해 위임합니다.

- 판정이 "수정 필요"면: 수정 필요 항목만 추려 `frontend-builder`에 재위임 → 다시 `qa-reviewer` 검수. **이 루프는 최대 2회**까지만 반복하고, 그래도 남는 항목은 보고서의 "남은 확인 질문"에 기록합니다.
- 판정이 "통과"면 5단계로 갑니다.

## 5단계 — 최종 보고 (오케스트레이터 직접)

```txt
완료:
- 브리프: (경로, 신규/갱신 여부)
- 바꾼 파일:
- 가동한 에이전트와 핵심 기여: (에이전트별 1줄)
- 적용한 기준: (참고한 references/skills)
- 실행한 검사: (check_repo.py 결과, QA 판정)
- 범위에서 제외한 것(Won't):
- 남은 확인 질문:
```

보고 후 "결과나 팀 구성에서 개선하고 싶은 점이 있는지" 피드백 기회를 한 번 제공합니다. (강요하지 않음)

## 에러 핸들링

- 분석 에이전트 하나가 실패하면 1회 재시도, 재실패 시 해당 관점 없이 진행하고 최종 보고에 누락을 명시합니다.
- 역할 간 상충 결과는 삭제하지 않고 지시서에 출처와 함께 병기한 뒤, 오케스트레이터의 결정과 사유를 남깁니다.
- frontend-builder가 지시서 일부를 구현하지 못하면 사유를 받아 최종 보고에 남기고, QA 요구사항 목록에서도 그 사실을 반영합니다.

## 금지 사항

- 서브에이전트를 호출하지 않고 "각 관점을 고려했다"고만 말하는 것
- qa-reviewer 통과 전에 "완료"라고 보고하는 것
- Won't 항목을 사용자 몰래 구현하거나 몰래 빼는 것
- 브리프 없이 1단계로 넘어가는 것

## 테스트 시나리오

**정상 흐름**: "숙소 검색/예약 페이지 만들어줘" → 0단계에서 `briefs/travel-booking.md` 로드(예시 브리프와 부합) → 6명 병렬 분석 → 지시서 → builder 구현 → QA 통과 → 보고.

**에러 흐름**: QA가 "필터 `data-*` 값과 데이터 코드값 불일치"로 수정 필요 판정 → 해당 항목만 builder 재위임 → 재검수 통과 → 보고. 2회 루프 후에도 실패하는 항목은 "남은 확인 질문"으로 보고.
